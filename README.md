# oeds-re — восстановление исходного кода Orcs & Elves DS

Исходный код DS-версии Orcs & Elves (США, YOEE), восстанавливаемый из arm9 картриджа
(`../load/arm9_main.bin`, база 0x02000000) по декомпиляции Ghidra (`../arm9_usa.c`), с именами
из строк игры, её отладочных текстов и сопоставления с BREW-версией (oe-re). Оригинал был на C++
(`Applet.cpp`, `Game.cpp`, `Render.cpp`, `ScriptThread.cpp`, …); здесь, как в oe-re, это C:
метод `Class::method(...)` — функция `Class_method(Class *self, ...)`.

Найденное по ходу переносится в модуль игры клиента (`oe-client/src/cgame_oeds`).

## Что где лежит

```
include/oeds.h        восстановленные типы (смещения DS) и прототипы
restored/<адрес>.c    восстановленные функции, по одной на файл
src/<Файл>.c          все функции исходного файла в порядке адресов (генерируется):
                      восстановленные — как в restored/, остальные — декомпиляция Ghidra в #if 0
src/sdk/head.c, tail.c   Nitro SDK и библиотека C до и после кода игры (не восстанавливаются)
map/functions.tsv     каждая функция: адрес, размер, файл, имя, BREW-аналог, откуда взят файл
map/files.tsv         диапазоны адресов файлов в порядке линковки
tools/build_tree.py   генератор src/ и map/ (python build_tree.py)
```

## Как разрезан arm9 на файлы

Линкер NDS кладёт функции одного объектного файла подряд, а файлы — почти по алфавиту:
Util, App, Applet, Camera, Canvas, Combat, CombatEntity, Entity, EntityDefManager, EntityMonster,
Game, Hud, Player, Render, ScriptThread, Sound, Stream, MenuSystem, TextureMappings, Text. Отдельного
Random нет: случайные числа — генератор App (+0x10).
Имена девяти файлов есть в самой игре (тексты ассертов: `Util.cpp`, `Applet.cpp`, `Entity.cpp`,
`EntityDefManager.cpp`, `Game.cpp`, `Render.cpp`, `ScriptThread.cpp`, `Text.cpp`,
`TextureMappings.cpp`), остальные взяты из классов BREW-версии.

`build_tree.py` берёт класс из имени функции (у восстановленной — из её имени в `restored/`). Безымянные функции между двумя функциями одного
класса относит к нему. Между классами A и B ставит разрез там, где вызовы (кто вызывает функцию и
кого вызывает она) сходятся лучше всего. Одиночное имя чужого класса среди функций другого класса
считается ошибкой сопоставления. Неверные имена Ghidra перечислены в `DISTRUST`
(например, `App_getMemUsed` посреди SDK). Файл, оказавшийся в нескольких диапазонах
(`map/files.tsv`, столбец note), надо проверить: обычно это неверное имя.

Код игры начинается с `Util.cpp` на 0x02012e18. До него (0x02000000–0x02012e18) лежат Nitro SDK
(файловая система, ОС) и библиотека C (`printf`, `strtod`), после 0x02066f54 — снова библиотеки.

## Как восстанавливать функцию

1. Найти её в `src/<Файл>.c` (сырой текст в `#if 0`) и в `map/functions.tsv`.
2. Константы из литерального пула, которые Ghidra показывает как `DAT_…`/`PTR_…`, читать прямо
   из `arm9_main.bin`. Таблицы переходов, которые Ghidra не раскрыл, дизассемблировать скриптом
   `../scripts/DumpAsm.java`.
3. Записать C в `restored/<адрес>.c` (с комментарием, что она делает), дополнив `include/oeds.h`
   нужными полями структур (со смещениями).
4. `python tools/build_tree.py`, затем проверить компиляцию:
   `cl /c /W3 /Iinclude src\<Файл>.c` (или gcc).

Отладочные тексты в коде игры (`Dbg_printf("script#%d.%d paused", …)`) и аргументы её макроса
ошибок (`"EFAILED"`, `"Util.cpp"`, строка, `"DirToAngle"`) сохранены: они дают настоящие имена
функций, например `Camera::Update`, `Util::DirToAngle`, `Util::AngleToDir`.

### Память сохранений (SaveData, Game+0xb290): 23 из 30 функций

Класс в конце кода игры (0x0206660c…0x02068070; генератор раньше относил его к SDK). Память картриджа
поделена на блоки со счётчиком владельцев:

| смещение | что |
|---|---|
| 0x000 | 0x081d1410 |
| 0x004 | контрольная сумма заголовка (на время записи — 0: прерванное сохранение видно) |
| 0x008 | заголовок: 64 счётчика блоков |
| 0x048 + слот·0x80 | таблица слота: сумма, 16 смещений блоков (0 — настройки, 1/2 — запись игрока: сохранение и начало уровня, 3 — мир игры, 4+карта — мир карты) |
| 0x248 + i·0x40 | 4 блока настроек |
| 0x348 + i·0x200 (i = 4…11) | 8 блоков игрока |
| 0x1348 + i·0x1000 (i = 12…63) | 52 блока миров |

Слоты 0…2 — сохранения игрока, слот 3 — идущая игра (его таблица и в памяти). Запись идёт в слот 3
с копированием при записи (общий с сохранением блок заменяется новым), затем выбранный слот
становится копией слота 3 — копируются только ссылки. Загрузка — наоборот. Контрольная сумма —
Флетчер по знаковым 16-битным словам с переносом каждые 360 слов.

### Заклинания жезла (SpellCircle, 0x02068070…)

Круг заклинаний на сенсорном экране — объект 0x02093bfc. Четыре заклинания — оружие самого круга
(+0x3c, по 0x24 байта), записи значков — 0x0206bd00 (место, имя в CodeStrings, последовательность):

| значок | заклинание | последовательность | урон | энергия | эффект |
|---|---|---|---|---|---|
| вверх (0) | FORCE | вниз, вправо, влево, вверх | 80 | 80 | 0x1c: отбрасывает всё на 8 клетках вокруг цели (3 клетки сбоку, 2 по диагонали) |
| вниз (1) | FIRE | вверх, вправо, влево, вниз | 100 | 80 | 0x1d: брызги 3×3 (бока ½, углы ¼), поджигает |
| влево (2) | LIGHTNING | вправо, вниз, вверх, влево | 80 | 35 | 0x1e: урон |
| вправо (3) | STUN | влево, вверх, вниз, вправо | 50 | 80 | 0x1f: монстр стоит 6 ходов (флаг 0x2000, +0x44 += 6) |

Заклинание выучено — бит в Player+0x84 (Player_give тип 11: ещё +100 энергии, «New Spell!», звук 0xdc).
Энергия — Player+0x3e (заряды кристаллов, ammo 1), предел 13·(дальняя карта − 6000) + 10, не больше 99.
Ход: значок выученного и доступного по энергии заклинания (звук 0xd9) → мигает первый значок
последовательности (раз в 300 мс), верный — 0xdb и следующий, неверный — 0xd8, «invalid spell
sequence» (CodeStrings 26) и заново; после четвёртого — 0xda, имя («LIGHTNING!») 1,2 с, затем действие
меню 0x2a: оружие 0 (жезл) := оружие заклинания (0x02069d6c) и обычная атака вперёд. Снаряд — тайл 0xe1,
вспышка — 0xf3, кадр = эффект − 0x1b.

### Почему странно выглядел гном (призрак)

Тайл 0x42 — программа «призрак»: модель полупрозрачная (альфа ~16/31) и покачивается. Команда программы
0x16 (0x0204be88) задаёт POLYGON_ATTR: биты 0–1 байта флагов — какие стороны рисовать (1 — задние,
2 — передние, 3 — обе), бит 4 — свет, биты 2–3 — режим; каждый вызов берёт новый номер полигона.
Клиент рисовал все полигоны DS двусторонними, и сквозь полупрозрачное лицо была видна изнанка капюшона.
Теперь стороны учитываются (материал с cull); из-за смены осей DS→Quake «передняя» сторона DS — это
cull front в шейдере Quake.

## Перенесено в cgame_oeds

- команды сценариев DS: LAUNCHFLAMES (0x6a), RESPAWNMONSTER (0x6d), LERPSPRITETOOPENTILE (0x71),
  проверка «по спрайту» у ABORTUNLESSTILEOPEN (0x72, бит 18), коллекция игрока (0x75);
- ABORTUNLESSTILEOPEN трассирует с маской 0xfdaf, как DS; TRIGGERIF передаёт в `executeTile`
  флаг 0x2000000 своей команды;
- `Entity_findOpenAdjacentTile`, `Combat_launchFlames`;
- по `executeEvent`: команды DS 0x69–0x77 раньше отбрасывались проверкой `opcode >= EV_COUNT` и теперь
  исполняются; 0x67 (SHOW) будит показанного монстра; 0x77 ставит движению флаг 4; EV_SET (0x6f)
  ставит флаг при `arg >> 5 != 0`; TRIGGER и TRIGGER в своём потоке передают флаг 0x2000000;
  0x62 SHOWHAMMERCUES — это BREW 0x61;
- EV_AIGOAL как в DS (монстр выходит из боя, сразу думают только цели 3 и 10, бегство — 20 ходов);
  поток, который он поставил на паузу боем, теперь продолжается, когда ход монстров кончился
  (`ScriptThread_signal` из `Canvas_combatTurnDone`); раньше такой поток не просыпался;
- флаги движения спрайта из `Game_updateLerpSprites` DS: 2 — сущность уже на новой клетке
  (LERPSPRITETOOPENTILE ставит его, и движение больше не перекладывает её по клеткам), 4 — команда 0x77,
  спрайт не переходит в другой лист BSP;
- `Game_trace` как в DS: eType 11 подтипа 127 загораживает клетку (подтипа 0 — нет), спрайт с битом DS 0x10000000
  стоит, а не висит на стене, eType 10 подтипов 5/9/10 меряется от места, где нарисован;
- дверь DS всегда уезжает на клетку вбок за 250 мс (BREW поднимала её в низкий потолок, а потолок карт DS низкий);
- заклинания жезла (ds_spells.c): Q — круг поверх вида, выбор мышью или стрелками и Enter; правила DS
  (выученные заклинания, энергия, последовательности, выстрел жезлом с оружием заклинания, огонь, сила,
  оглушение); выученные заклинания и флаги DS теперь сохраняются (хвост записи игрока, «DSX1»);
  нет: рисунков круга DS, искр от стилуса, горения;
- отсечение сторон моделей DS в движке (cl_dsmap.c) — исправленный вид призрака-гнома.
